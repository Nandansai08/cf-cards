# Contributing to Codeforces Cards

Thanks for taking the time to contribute. This is a small, friendly project —
issues, bug reports and pull requests are all welcome.

By participating you agree to abide by our [Code of Conduct](CODE_OF_CONDUCT.md).

## Getting set up

You need Node.js 22 or newer — some TanStack packages declare `node >=22.12`.

```sh
git clone https://github.com/Nandansai08/cf-cards.git
cd cf-cards
npm install
npm run dev
```

The dev server prints a local URL. There is no backend to run and no
environment variables to set — the app talks directly to the public Codeforces
API from the browser.

## Checks to run before you push

```sh
npm run lint        # eslint + prettier, must report zero errors
npx tsc --noEmit    # typecheck, must be clean
npm run build       # production build, must succeed
npm run build:pages # the static build that actually gets published
npm test            # end-to-end tests
```

CI runs exactly these on every pull request. `npm run format` will fix
most lint complaints for you, since formatting is enforced through prettier.

## How the project is laid out

| Path                    | What lives there                                                |
| ----------------------- | --------------------------------------------------------------- |
| `src/routes/`           | Pages. File-based routing — the filename _is_ the URL           |
| `src/routes/__root.tsx` | App shell: `<head>`, nav, footer, providers                     |
| `src/lib/codeforces.ts` | Codeforces API client — fetching, caching, rate limiting        |
| `src/lib/fut.ts`        | The rating engine: attributes, OVR, tiers, badges, achievements |
| `src/lib/roster.ts`     | Locally saved cards, used by the leaderboard                    |
| `src/components/fut/`   | The card itself and the player profile view                     |
| `src/components/site/`  | Nav and footer                                                  |
| `src/components/ui/`    | shadcn/ui primitives                                            |
| `src/styles.css`        | Design tokens, tier palettes, animations                        |

`src/routeTree.gen.ts` is generated by TanStack Router. Never edit it by hand —
it is rewritten whenever you add or rename a route.

## Conventions

**Colours come from tokens, never hardcoded.** `src/styles.css` defines every
colour as an oklch semantic token (`--primary`, `--surface`, `--tier-a`, …).
Use the Tailwind classes that map to them (`bg-surface`, `text-primary`) so the
theme stays consistent. A raw hex value in a component is a bug.

**Only add a shadcn/ui component when you use it.** The `src/components/ui/`
folder is deliberately trimmed to the primitives the app actually imports. Add
new ones with the shadcn CLI as you need them rather than in bulk.

**Keep the card the centrepiece.** The player card is the product. Changes that
make it look worse on mobile, or that push it below the fold, are unlikely to
be merged.

## Tests

```sh
npm test        # headless
npm run test:ui # Playwright's UI mode, good for debugging a failure
```

Playwright starts the server itself, so there is nothing to run first. Two
things about the setup are deliberate:

- **Tests run against the production build** (`npm run build:pages`, served by
  `scripts/serve-static.mjs`), not the dev server. That is what actually ships,
  and in dev the client loads hundreds of unbundled modules, so hydration is
  slow enough to make every interaction test flaky.
- **The Codeforces API is always stubbed** (`tests/fixtures/codeforces.ts`).
  Tests must never hit codeforces.com: it would make them slow, flaky and
  dependent on live data, and it would put load on a public API we don't own.
  Demo players come from a seeded PRNG, so a handle always produces the same
  card and assertions can be exact.

Browsers are not bundled with the install. `npx playwright install chromium`
fetches one, or set `CHROMIUM_PATH` to a browser you already have.

When you fix a bug, add the test first and **watch it fail** before you fix it.
The pack-reveal regression in `tests/pack.spec.ts` is a cautionary tale: the
first two versions of that test passed against the broken code, once because
they reloaded the page (which wipes the query cache the bug depends on) and
once because the assertion matched an unrelated chip in the form.

## Regenerating the README screenshots

```sh
npm run screenshots
```

Output lands in `docs/screenshots/`. This is a separate Playwright project
(`tests/screenshots.spec.ts`), so `npm test` never runs it, and it uses the same
stubbed demo players as the tests. If you change the UI in a way the screenshots
show, please regenerate them in the same pull request.

## Working on the rating engine

`src/lib/fut.ts` has one rule above all others: **it must stay deterministic.**

- The same handle with the same Codeforces history must always produce the same
  card. No randomness, no time-of-day dependence, no fabricated numbers.
- Every attribute must be explainable in one sentence, and that explanation
  belongs in `ATTR_META` so it shows up on `/about`.
- Volume-based inputs (problems solved, contests played, tags, active months)
  go through `logNorm` so that a huge problem count adds diminishing value
  instead of dominating the card.
- Cosmetic card customisation must never change a computed stat.

If you change a formula or a weight, update the matching copy on `/about` in
the same pull request, and say in your PR description how a few real handles
move as a result.

## Working with the Codeforces API

- Only public endpoints: `user.info`, `user.rating`, `user.status`. No API
  keys, no authentication, no scraping of pages.
- The app is deployed as a static site with no server, so anything you add has
  to work from the browser alone. Don't introduce a server route or a build-time
  secret.
- Requests go through the queue in `src/lib/codeforces.ts`, which serializes
  calls with a gap and retries on rate limits. Don't call `fetch` against
  Codeforces directly from a component.
- Responses are cached in `localStorage` for 30 minutes. If you add an
  endpoint, cache it too.
- Handle failure properly: invalid handle, network error and rate limit all
  need a friendly message, never a raw error string.
- Never invent data. If Codeforces doesn't publish a user's country or
  organization, show nothing rather than a guess.

## Pull requests

1. Branch off `main`.
2. Keep the change focused — one concern per pull request.
3. Run the three checks above.
4. Include a screenshot or short clip for anything that changes the UI, and
   check it at a mobile width too.
5. Fill in the pull request template.

Small, well-described pull requests get reviewed fastest. If you're planning
something large, open an issue first so we can agree on the approach before you
spend the time.

## Reporting bugs

Open an issue using the bug report template. The single most useful thing you
can include is **the Codeforces handle that reproduces it** — most bugs in this
project only show up for a particular shape of data (unrated users, users with
no submissions, very old accounts, handles with unusual characters).

## Security

Please don't open a public issue for a security problem. See
[SECURITY.md](SECURITY.md) for how to report one privately.
